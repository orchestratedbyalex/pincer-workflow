# PINCER 1.0 Harness Builder Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn PINCER from a fixed installed pipeline into a kit that interviews a project, writes its agreement, and runs the pipeline that agreement describes.

**Architecture:** A dependency-free Node core under `template/scripts/pincer/` (parser, ticket lifecycle with receipts and acceptance, status with stage gates, evidence validator, recon, blueprint writer, generator) behind four thin entry points. A library under `template/.claude/pincer/library/` of stage skills (SKILL.md, prompts/, formats/) and agents; the blueprint writes `harness.json` and the project's copies, and the Codex and Copilot files are generated from those copies. Everything in the old runtime that defended the fixed pipeline is deleted.

**Tech Stack:** Node 22+ CommonJS for the kit (`.cjs`, `node:` modules only), ESM for the installer and tests, bash for the two wrappers and the hooks, markdown and JSON for everything else.

**Spec:** `docs/superpowers/specs/2026-10-20-harness-builder-design.md`

## Global Constraints

- Node `>=22`; `package.json` declares no dependencies; every `require` is `node:` or a relative sibling.
- `template/` is the single source. Project copies, Codex skills and Copilot prompts are generated by `node scripts/pincer/cli.cjs generate`; a test fails on stale shipped copies.
- No `@` imports in anything Codex or Copilot reads. The Claude import stays only in `CLAUDE.md`.
- The floor: `done` only after a script-stamped passing receipt; acceptance recorded with the person's name and words. The hook keeps `pincer-ticket.sh` the only writer of those fields on Claude Code.
- Course text is paraphrased, never copied; the six heading names (Systems, Current pipeline, Handoff artifacts, Simplify, Responsibility, Repo) are used as is.
- Default homes: `specs/`, `tickets/`, `evidence/`, `harness.json` at the root. No `.pincer/` directory, no `.pincer/` ignore line, no hook rule for it.
- The plugin channel is paused: `plugin/`, `.claude-plugin/` and `scripts/build-plugin.sh` are removed. The wiki is frozen. Open PRD v8 tickets are marked superseded.
- Branch `feat/harness-builder`, local only. No push, no publish. Version `1.0.0`.
- Commit messages end with the two attribution lines used so far on this branch.

## Review Focus

1. `harness.json` hand-edited into invalid JSON or an unknown stage name: every entry point prints `harness.json: <reason>` and exits 3, never a stack trace. (Task 3)
2. Recon on a directory with no `.git`, no remote or no `gh`: still classifies, lists what it could not see, exits 0. (Task 8)
3. `write` re-run on an `AGENTS.md` the developer edited outside the agreement markers: their text survives byte for byte. (Task 9)
4. `accept` words containing `#`, quotes or a newline: stored on one frontmatter line, read back intact by status, and the hook still treats the field as protected. (Task 4)
5. `generate` re-run after the developer edited a project copy: the edit stays and a `.new` sidecar appears, never an overwrite. (Task 10)

- Schema 1 (pin these fields; the builder may add optional ones):

```json
{
  "schema": 1,
  "project": { "name": "", "kind": "greenfield|brownfield", "reason": "" },
  "people": [ { "name": "", "role": "", "accepts": true } ],
  "systems": { "forge": "github|none|other", "remote": "", "ci": false, "deploy": "", "secrets": "" },
  "repo": { "branches": "per-ticket|main", "pr": false, "merge": "merge|squash|rebase", "protection": "", "checks": [] },
  "homes": { "specs": "specs", "tickets": "tickets", "evidence": "evidence" },
  "stages": {
    "plan":     { "on": true, "spec": "file|forge", "gate": "" },
    "narrow":   { "on": true, "tickets": "file|forge" },
    "code":     { "on": true, "implementer": false },
    "evaluate": { "on": true, "where": "local|pr", "evidence": true },
    "release":  { "on": true, "audit": "tree|pr" }
  },
  "roster": { "plan": [], "narrow": [], "code": [], "evaluate": [] },
  "open": [],
  "firstJob": ""
}
```

Validation rules: `schema === 1`; `project.kind` in the two values; at least one person with `accepts: true`; every stage key in `STAGES` minus the always-on two; every roster name in `AGENT_NAMES` and every roster stage in `stages`; every home a relative path without `..`; `repo.merge` and `stages.*` enums as listed. Unknown top-level keys are kept, not rejected.
