## Findings

1. **The exception wording does not say which environment "run directly"
   means.** The code playbook's condition is that the Verification block
   passes when run directly. In the negative case the block failed under the
   session's `PATH` and passed with the real `npm` binary, and the session
   chose the latter. That is defensible when the fault is a shim, but the same
   reasoning would let an agent talk past a real environment failure. A
   follow-up could add that the recorded failure must be explained by a
   working-tree change that has since been reverted, and that any other cause
   is fixed first and then re-run through `verify`. Not changed in this PRD;
   logged for the wiki.
2. **Operator note.** An injected environment fault leaks its origin: the shim
   path under the operator's scratchpad was found and reported. A persistent
   negative case needs a fixture with an external dependency (a service, a
   date, a network call) so the failure cannot be bypassed by choosing a
   different binary.
3. **Operator note.** Updating the kit in an evaluated fixture is a commit
   after the candidate and forces a re-evaluation before any candidate-bound
   scenario can run. Budget one evaluate session per kit revision.
