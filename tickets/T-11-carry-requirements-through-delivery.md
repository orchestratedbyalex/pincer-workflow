## Requirements
- PRD template gains a core `Requirements` section: each entry is `### R-NN — title` with observable acceptance scenarios, relevant failure paths and existing behavior to preserve. The Problem/Solution sections record the desired outcome, assumptions and exclusions, and either preserve or link the original brief.
- Plan playbook: assign stable `R-NN` IDs inside the selected PRD; never renumber on revision. When the user supplies a PRD, review it without replacing its meaning or IDs; if its structure needs adaptation, record a mapping table (`their ID/section → R-NN`) inside the PRD.
- Narrow playbook: write a `Requirement map` table in the narrow output and keep it in each ticket's Context (`Implements: R-01, R-03`). Every required scenario names an implementation owner (ticket) and an executable check or an explicit review method. Enabling work without a direct requirement states its purpose in the ticket Objective. Missing coverage and conflicting criteria are resolved with the user before implementation starts.
- Evaluate playbook: account for every `R-NN` as `delivered`, `blocked` or `deferred`. Required failed or unverified behavior blocks PASS; a limitation label does not convert a failed requirement into a pass. Deferral needs explicit user authorization recorded with the scope decision, and the revised candidate is re-evaluated. The playbook states that completeness and semantic adequacy of the mapping are an agent/reviewer judgment recorded in the evaluation, not a mechanical traceability engine.
- Ticket template: Context lists the requirement IDs the ticket implements.
- `test/workflow.test.js` asserts the new contract wording in plan, narrow, evaluate and both templates, and asserts that no playbook claims mechanical traceability.
